# Deploying Tracer to Render

The repository contains a `render.yaml` blueprint that creates three things in
one step: the Flask API, the static React frontend, and a PostgreSQL database.

**Roughly 25 minutes of setup, plus 10–20 minutes to load the data.**

---

## Why PostgreSQL and not MySQL

The project runs on MySQL locally, which is what Chapter Three documents.
Render does not offer managed MySQL, so the hosted copy uses PostgreSQL.
Nothing in the application changed: SQLAlchemy generates the SQL for whichever
dialect the connection string names, so the models, queries and routes are
identical. The only code that needed dialect awareness was the bulk loader,
which used a MySQL-specific statement to suspend foreign-key checks.

If asked, this is the honest one-liner:

> The system is database-agnostic through SQLAlchemy. It runs on MySQL locally,
> as described in the report, and on PostgreSQL in the hosted demonstration,
> because that is what the hosting provider offers. No application code differs.

## Step 1 — Deploy

1. Push `main` to GitHub (already done).
2. Go to **dashboard.render.com** → **New** → **Blueprint**.
3. Connect the repository `HabeebAdewole/fraud-detection-system`.
4. Render reads `render.yaml` and shows three resources: `tracer-db`,
   `tracer-api`, `tracer-web`. Click **Apply**.

`SECRET_KEY` and `JWT_SECRET_KEY` are generated by Render, and `DATABASE_URL`
is wired to the database automatically. Nothing to paste.

The first build takes 5–10 minutes, mostly installing scikit-learn.

## Step 2 — Load the database

The blueprint creates an empty database. The Elliptic CSVs are 657 MB and are
not in the repository, so the load runs **from your machine** against the
hosted database.

Get the connection string: Render → `tracer-db` → **External Database URL**.

```bash
# from the repository root, in the venv
set DATABASE_URL=<paste the External Database URL>

backend\venv\Scripts\python.exe ml_pipeline\elliptic_load_db.py
cd backend && venv\Scripts\python.exe seed_users.py
```

The loader detects that the database is remote and sends larger batches.
Expect 10–20 minutes for 203,769 transactions and 234,355 edges over a home
connection. It is idempotent — safe to re-run if it drops out.

## Step 3 — Check it

```bash
curl https://tracer-api.onrender.com/api/health
```

```json
{ "status": "ok", "environment": "production", "database": "ok" }
```

Then open **https://tracer-web.onrender.com** and sign in with the seeded
accounts.

## Two things to know about the free tier

**The API sleeps after 15 minutes of inactivity.** The first request afterwards
takes about 50 seconds while the instance wakes and reloads the 162 MB of model
artifacts. Every request after that is fast. This is fine for a portfolio link;
it is not fine for a live demonstration in front of an audience — open the page
a minute beforehand to wake it.

**Render's free PostgreSQL is deleted after 30 days.** For a link that has to
keep working, point `DATABASE_URL` at a provider whose free tier persists —
Neon and Supabase both offer one, both are PostgreSQL, and both work with the
URL normaliser already in `config.py`. Remove the `databases:` block from
`render.yaml` and set `DATABASE_URL` manually in the service's environment.

## Changing the demo credentials

The seeded accounts (`admin` / `admin123`, `analyst` / `analyst123`) are fine
for a demonstration but are published in this repository. For anything public,
edit `backend/seed_users.py` before running it, or change the passwords through
the admin panel afterwards.

## Environment variables

| Variable | Set by | Purpose |
|---|---|---|
| `ENV` | blueprint | `production` enables the strict posture |
| `SECRET_KEY` | Render | Flask session signing; boot fails without it |
| `JWT_SECRET_KEY` | Render | Token signing; boot fails without it |
| `DATABASE_URL` | Render | Normalised automatically; TLS added for remote hosts |
| `CORS_ORIGINS` | blueprint | Restricts the API to the frontend origin |
| `VITE_API_URL` | blueprint | Baked into the frontend at build time |

Changing `CORS_ORIGINS` requires a redeploy of the API; changing
`VITE_API_URL` requires a rebuild of the frontend, since Vite inlines it.
